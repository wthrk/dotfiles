根拠:
- 対象: 現行ブランチ `fix/bws-provisioning-inputs-issue-44` の未コミット worktree を含む current worktree。対象モジュールは `rust/dotfiles-cli/src/secrets/` 全体として読み、BWS / YubiKey / Bitwarden Password Manager / GPG backup / password-store provisioning の責務分配を `docs/architecture/hexagonal-implementation-rules.md` の哲学に照らして確認した。
- BWS の固定 project / secret 名、一意解決、0件/複数件の failure 化は `domain::bws` に閉じている。`BwsSecretName::key` / `matches_candidate` / `resolve_id` と `BwsProjectName::resolve_id` が対象同一性と候補数規則を表し、コメント上も SDK 詳細ではなく復旧対象の業務規則として位置付けている（`rust/dotfiles-cli/src/secrets/domain/bws.rs` 1-4, 15-58, 103-132）。
- BWS SDK 接続と平文 access token の所有 buffer / zeroize / core-dump 抑止は `support::protection::bws` に限定され、project/secret lookup rule や外部確認 plan を扱っていない。`login_client_with_access_token` は SDK login と token buffer zeroize、`BwsClientSession::get_password_store_remote` は SDK 返却値を zeroize 管理へ入れて domain parser に渡す境界であり、support が固定 key の一意解決や verify plan を所有していない（`rust/dotfiles-cli/src/secrets/support/protection/bws.rs` 1-14, 60-80, 81-104）。
- BWS adapter は `BwsClientPort` の実装として SDK list/get/create/update を port 境界型へ翻訳している。project/secret 候補は `BwsLookupCandidate` へ変換し、ID は opaque domain 値へ変換し、secret value は `GpgBackupEnvelope` / `PasswordStoreRemote` / `BackupUpdateGuard` へ翻訳している。`BwsSecretName::key()` の利用は SDK request key への翻訳であり、対象一意性や create/update 可否の判断を adapter が中心化していない（`rust/dotfiles-cli/src/secrets/adapters/bw.rs` 1-5, 55-133, 136-183, 202-282）。
- provisioning の use case は `application::run_provision_password_store_remote` にあり、BWS access token 入力、project 解決、同名 secret の 0/1/複数分岐、上書き確認、URL 入力と domain 検証、create/update の順序を application が所有している。YubiKey storage はこの provisioning 経路に渡されず、復旧用 `bws-access-token` と保管側 create/update token の責務が分離されている（`rust/dotfiles-cli/src/secrets/application/run_provision_password_store_remote.rs` 13-35, 36-105）。
- GPG backup の primary 登録と spare recipient 追加は、BWS token 入力と project/secret 解決を application が順序制御し、GPG keyring / cipher / YubiKey recipient / confirmation / BWS update は port capability として適用している。DEK 生成・暗復号は `BackupCipherPort` と support protection backend、recipient wrap/unwrap は `GpgRecipientPort` と YubiKey adapter、envelope schema・recipient 照合・stale guard は domain に分かれており、BWS adapter/support へ backup policy が逃げていない。
- restore-pass と verify-yubikey は復旧本線として、YubiKey storage から read 用 `bws-access-token` を取得してから BWS project/secret を domain rule で解決し、`password-store-remote` / `gpg-secret-key-backup` を typed port で取得する。Password Manager login は `BwLoginPort`、BWS check は `BwsClientPort` と `GpgRecipientPort`、password-store clone/readiness は Git / password-store / GPG keyring port へ分かれ、外部製品ごとの具体操作が application に直接混入していない。
- `ports` は外部機能ごとに分かれており、BWS API、Bitwarden Password Manager CLI、YubiKey storage / recipient、GPG keyring / cipher / ssh-agent、password-store filesystem / git clone、process I/O / report / confirmation が別 capability として宣言されている。port は「何を必要とするか」の境界を表し、SDK 型や CLI child process 詳細、prompt 実装、filesystem 走査実装を流出させていない。
- `entrypoint` / composition root は CLI option の parse と command-to-usecase dispatch、adapter concrete の組み立てに限定されている。`PassRemoteCommand::Register` は `ProvisionPasswordStoreRemoteCommand` へ変換され、`process_io` / `bws_client` / confirmation port を渡すだけで、BWS SDK や YubiKey device 操作を直接実行していない。
- internal backend stub は BWS、Bitwarden Password Manager login、YubiKey、GPG、Git で adapter-local feature selection に分かれ、コメント上も production build 非混入、runtime real/stub 分岐なし、同一 `dotfiles` binary 経由、BWS/YubiKey port stub 非共有を明記している。全体設計上、stub の存在が production command path を分岐させる構造には見えない。

Rationale:
- モジュール全体は coherent design か: はい。`secrets` モジュールは entrypoint が command 境界、application が use case 順序、domain が固定名・一意解決・envelope / password-store / verification の意味、ports が外部 capability、adapters が SDK/CLI/device/filesystem/process 変換、support が protection / crypto / process primitive を担う構造として読める。BWS/YubiKey/Password Manager/GPG backup/provisioning は複数製品を跨ぐが、製品別 adapter を並べただけではなく、復旧・保管の業務規則が domain/application に集約されている。
- 責務は層をまたいで一貫して分配されているか: はい。固定 BWS key/name と一意解決は domain、create/update/verify/restore の進行は application、SDK request / UUID / child process / PIV / git2 / filesystem は adapter、平文 token・password・DEK などの保護境界は support へ置かれている。特に remediation 対象になりやすい BWS support には、固定 secret key の一意解決、0件/複数件の domain failure 化、取得対象の過不足判定、`verify-yubikey --check bws` の外部確認 plan は残っていない。
- layer relation は全体として意味をなすか: はい。application は port trait に対して順序を適用し、adapter は port 境界型と外部技術型を翻訳し、domain は SDK / process / device を知らない。`ProtectedSecret` は secret carrier として domain/port/application を跨ぐが、平文借用と外部 SDK/CLI への注入は protection/adapter 境界内へ閉じられており、domain が技術実装を知る形にはなっていない。
- 機械的分離に頼っていないか: 頼っていない。ファイル分割は `run_provision_password_store_remote`、`run_register_gpg_backup_primary`、`run_add_gpg_backup_spare`、`run_restore_pass`、`run_verify_yubikey_with` のように use case 境界で分かれ、domain も BWS lookup、GPG backup envelope、password-store readiness、Bitwarden login 入力値といった意味単位で分かれている。adapter/support へ「薄い port を保つための業務判断」を押し込んだ構造ではない。
- support が逃げ場になっていないか: なっていない。`support::protection::bws` は SDK が要求する owned plaintext token と secret value buffer の zeroize / session 境界を閉じるための dedicated backend 操作であり、BWS project/secret の同一性、更新確認、verify plan は application/domain/port 側にある。`support::protection::gpg_backup` や sealed blob 系も暗号・保護境界として読め、GPG backup の recipient 追加や restore の進行は application/domain に残っている。
- 新しい use case / adapter を追加するとき自然に置き場を判断できるか: はい。新しい BWS secret 種別なら domain の閉じた secret 名と port capability / application use case の追加、新しい外部確認なら verification domain と application check branch / dedicated port、新しい backend 技術なら adapter または protection backend、という判断が既存構造から自然に導ける。
- 有能なアーキテクトが全体を読んだとき coherent design と呼ぶか: はい。複数の外部製品を横断するが、復旧対象の意味と手順、外部 I/O 翻訳、平文保護境界が一貫して分離されているため、個別ルールを通しただけの部品の山ではなく、hexagonal architecture の哲学に沿った設計として成立している。
