# 運用整合レビュー（Bitwarden Secrets Manager / fix/bws-provisioning-inputs-issue-44）2026-06-04

判定: 要修正
判定要約: BWS 初期 provisioning 手順が `dotfiles-secret-recovery` project の作成または既存化 gate を監査可能に固定しておらず、script/CLI だけでは初回実行手順が完走不能になる
根拠:
- 対象: branch `fix/bws-provisioning-inputs-issue-44` の current worktree（未コミット差分を含む）。確認対象は `scripts/provision-secret-recovery-source.sh`、`docs/secret-recovery/initial-provisioning-runbook.md`、`README.md`、`docs/secret-recovery/README.md`、`docs/secret-recovery/secret-recovery-spec.md`、`docs/secret-recovery/bitwarden-secrets-manager-design.md`、および BWS provisioning / verify 経路の Rust 実装。
- 直接確認した運用上成立している点: BWS 登録・更新用 token と YubiKey 保存用復旧 token は文書上分離され、token 入力は CLI 引数ではなく hidden prompt / pipe 経由に固定されている。`pass-remote register` と `gpg-backup register` は YubiKey storage から provisioning token を読まず、`BwsAccessTokenInputPort` から取得する。`pass-remote` / `gpg-backup add-spare` の更新系は更新前 guard を取得し、更新直前の guard 一致を条件にする stale overwrite prevention を持つ。`verify-yubikey --check bws` は BWS 取得成功だけでなく `gpg-secret-key-backup` envelope と接続中 YubiKey recipient matching を確認する。
- Finding 1: `docs/secret-recovery/initial-provisioning-runbook.md:37` は Bitwarden Secrets Manager provisioning を **[CMD]** `dotfiles secrets gpg-backup register` / `add-spare` / `pass-remote register` または `scripts/provision-secret-recovery-source.sh` で実現済みとして分類し、同 `:83-88` は BWS への `password-store-remote` / `gpg-secret-key-backup` 登録を script/command 手順として案内している。しかし、同 runbook には BWS project `dotfiles-secret-recovery` を事前に作成する手動 gate、または command が project を作成する gate がない。
- Finding 1 の実装根拠: `scripts/provision-secret-recovery-source.sh:187-194` は `pass-remote register` と `gpg-backup register` を呼ぶだけで project 作成を行わない。Rust 側も `run_provision_password_store_remote.rs:51-53` と `run_register_gpg_backup_primary.rs:60-62` で `list_bws_projects` の結果から `BwsProjectName::DOTFILES_SECRET_RECOVERY.resolve_id(...)` を呼ぶ。`domain/bws.rs:126-130` および `:155-160` は一致 project が 0 件なら `bws project not found: dotfiles-secret-recovery` として失敗させるため、初期 project が存在しない新規 BWS 環境では、runbook が **[CMD]** として示す BWS provisioning は secret 作成まで到達しない。
- Finding 1 の運用影響: 初期プロビジョニングの最重要 gate である「復旧用 BWS project が存在し、secret 登録先が一意であること」が、手順上は command 実現済み扱い、実装上は事前存在必須という状態になっている。これは operator がどの時点で何を作成・確認すべきかを監査証跡として再現できず、role separation / gate 条件 / 完了判定で「runbook 通りに実行すれば BWS secret 登録が成立する」と判定できない具体的懸念である。
- 差戻し条件: どちらかに統一すること。選択肢 A: `dotfiles` / script が `dotfiles-secret-recovery` project の create-or-resolve を実装し、project 作成・一意性確認・secret 登録の結果を command 手順として監査可能にする。選択肢 B: project 作成は手動範囲として runbook / README / design に明示し、project 作成後に `list_bws_projects` で一意解決できることを BWS provisioning 前 gate として固定する。いずれの場合も `scripts/provision-secret-recovery-source.sh` の実行前提または実行内 preflight に反映し、初回実行時に project 未存在で失敗する挙動を operator の未記録裁量にしない。
