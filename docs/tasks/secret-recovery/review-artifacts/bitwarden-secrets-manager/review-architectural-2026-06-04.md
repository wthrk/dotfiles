- BWS の固定 project / secret 名、exact match、一意解決、0件/複数件の failure 化は `rust/dotfiles-cli/src/secrets/domain/bws.rs:1`、`rust/dotfiles-cli/src/secrets/domain/bws.rs:15`、`rust/dotfiles-cli/src/secrets/domain/bws.rs:103` に domain rule としてまとまっている。support/protection や adapter が固定名の意味づけや一意解決を所有する構造ではない。

Rationale:
- Whole-module question: Does the module structure express one coherent design, or is it a pile of files that only passed individual rules?
  Answer: coherent design. `entrypoint` が CLI parse 済み command と composition root から application へ渡し、`application/run_*.rs` が use case 順序を固定し、`domain` が BWS lookup / storage intent / envelope / password-store rule を持ち、`ports` が外部 capability を型付きに宣言し、`adapters` が BWS SDK・YubiKey PIV・bw CLI・GPG・Git・process I/O を翻訳している。対象ファイル群はルール通過の寄せ集めではなく、BWS/YubiKey/GPG/password-store の復旧フローを同じ層語彙で表現している。
- Whole-module question: Are responsibilities distributed consistently across layers, without scattering the same kind of responsibility across multiple layers/files, and without loading unrelated responsibilities into one file/layer?
  Answer: consistent. 固定 BWS 名と一意解決は `domain/bws.rs`、YubiKey storage 判定は `domain/storage.rs`、GPG envelope 判定は `domain/gpg_backup.rs`、password-store URL/readiness は `domain/pass_restore.rs` に集約されている。application は順序と停止条件だけを反復して適用し、adapter/support へ固定名解決・0件/複数件の業務判断・外部確認 plan を押し込んでいない。
- Whole-module question: Do layer relations (entrypoint -> application -> domain / port / adapter / support dependency direction and responsibility boundaries) hold as a whole in a way that matches the philosophy?
  Answer: yes. `secrets.rs` の composition root が concrete adapter を所有し、`entrypoint/dispatch.rs` が parse 済み option から domain command を作って application を呼ぶ。application は port trait と domain value を使って順序を進め、adapter は port 実装として SDK/process/device/filesystem へ接続する。`ProtectedSecret` は secret carrier と protection 境界として使われ、平文取り出しや SDK owned buffer は support/protection 内で完結している。
- Whole-module question: Is the module relying on mechanical separation instead of placing each processing unit in the prescribed responsibility boundary?
  Answer: no. たとえば BWS は単にファイルを分けただけではなく、lookup candidate と fixed name rule を domain、typed capability を port、create/update/fetch SDK 変換を adapter、access token / returned secret value の lifetime を support/protection に置く理由がコード上で追える。YubiKey storage も inspection/intent と adapter I/O 翻訳の対応が明確で、機械的な薄分けではない。
- Whole-module question: Are thin ports or thin adapters being achieved by moving responsibilities into a layer reserved for other work?
  Answer: no. `support/protection/bws.rs` は SDK login と zeroize/protected value 境界を担うが、BWS project/secret の固定名、一意解決、0件/複数件の failure、verify の外部確認 plan は持たない。adapter も SDK 型変換と port/domain 値への翻訳を担い、use case の create/update/restore/verify 順序は application 側に残っている。
- Whole-module question: If a capable architect reads the whole module, would they call it coherent design or disorganized?
  Answer: coherent design. BWS/YubiKey/Password Manager/GPG backup/provisioning が同一の hexagonal vocabulary（domain rule、application orchestration、typed port、adapter translation、support protection boundary）で表現されており、新しい復旧 secret や外部確認を追加する場合も、domain 名/値、typed port capability、application run function、adapter translation のどこへ置くかを自然に決められる。
- Whole-module question: When adding one new use case or adapter, does the current structure naturally accept it, or is the structure too inconsistent to decide where it belongs?
  Answer: naturally accepts it. 追加対象が BWS secret なら `domain/bws.rs` の対象名・一意解決、`ports/bw.rs` の typed capability、application の use case 順序、`adapters/bw.rs` の SDK 変換という既存経路に沿う。追加 adapter なら既存 port trait を実装する concrete adapter として差し替えられ、domain/application の業務規則を再配置する必要はない。
