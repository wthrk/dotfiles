# 実装実行規則

この文書は、実装担当が差分を作るときの正本である。

## 実装担当の強制義務

- 親オーケストレーターから実装作業を委譲された時点で、現在の実行者は実装担当である。委譲済みの同一 delegated task について active work item の再選定、オーケストレーター役割への切替、追加 subagent への再委譲を行ってはならない。
- `AGENTS.md` や `docs/task-governance/workflow.md` にあるオーケストレーター向け指示は、親オーケストレーターが委譲前に満たすべき条件として読む。実装担当はそれらを「自分も main agent なので再度オーケストレーションする」という意味に解釈してはならず、委譲された実装範囲を直接実行する。
- 実装担当は、次の正本を着手前に読み、適用しなければならない。
  - `docs/architecture/hexagonal-implementation-rules.md`
  - `docs/architecture/review-checklist.md`（ディレクトリ別公開面・依存方向・責務チェック項目 — レビュー時だけでなく実装時にも適用する）
  - `docs/task-governance/security-obligations.md`
  - active work item が要求する領域資料（`docs/tasks/<area>/...`）
  - `docs/tasks/<area>/work-items/<item>.md`
  - `docs/<area>/implementation-guidelines.md`（存在する場合）
- `docs/tasks/<area>/work-items/<item>.md` を読む際は、先頭から末尾まで全セクションを通読し、着手前要件・実装セッション制約・差戻し条件・完了条件を含む全ての指示を確認しなければならない。途中で読み飛ばしてはならない。
- `docs/tasks/<area>/work-items/<item>.md` に着手前要件が存在する場合、その要件がすべて満たされていることを確認してから実装に着手しなければならない。確認を省略したまま実装に着手してはならない。
- `docs/tasks/<area>/tasks.md` は、active work item が参照している場合に限り必須参照とする。未参照時は存在を前提にしてはならない。
- 局所的に動くことは、規約違反を残してよい理由にならない。
- 規約に合わない責務境界、依存方向、公開インターフェース境界は温存してはならない。

## 既存コード再読義務

実装担当は編集前に、次のカテゴリを再読しなければならない。

- `対象コードパス` に列挙されたファイル
- 変更対象ファイルから直接参照される共有型・インターフェース定義
- 変更対象の直接呼び出し元と直接呼び出し先
- 対応テスト（既存テストと追加・更新対象テスト）
- 同一作業項目で更新対象となる確認証跡・レビュー記録テンプレート
- 差し戻し再実装で親オーケストレーターから受け取った handoff 一式（未解消 finding 本文、reviewer role、verdict、file:line references、required fix、artifact path）

前回読んだ記憶だけで編集してはならない。再開時は再読を取り直す。
差し戻し handoff は入力正本の一部として扱い、要約へ置換してはならない。未解消 finding の本文とレビュー成果物を突合してから再実装すること。
この詳細 handoff は `current-cycle` review 後に新しい実装担当へ差し戻す remediation 委譲でのみ受け取る想定であり、reviewer 委譲の通常入力に流用してはならない。

## 実装時の判断規則

- 最小構成で済まそうとしてはならない。
- 最小差分化は目的ではない。
- 継承された既存構造の維持は目的ではない。
- `主成果物: 実コード差分` の作業項目では、実装十分性を先に結論してはならない。作業定義文書の `規約違反の解消対象` と `構造完了条件` に照らして現行コードを追跡し、未解消項目を残さないことをコード参照付きで示した場合に限り、十分性を記録できる。
- `状態: 未開始` かつ `主成果物: 実コード差分` の作業項目では、`追加差分不要` を先に結論してはならない。先に作業定義文書の完了条件・`規約違反の解消対象`・`構造完了条件` を基準として未解消項目と是正対象を洗い出し、その各項目の解消コード差分を示した場合に限り `追加差分不要` を記録できる。
- 現行構造がアーキテクチャ、仕様、作業定義に抵触する場合、適合構造への再設計を実装義務とする。必要ならモジュール境界や文書境界のゼロベース再編を行う。
- 修正範囲内の既存コードに規約違反が見えている場合、その違反を無視して局所差分だけを積んではならない。
- 修正範囲を跨いで直接必要な隣接コードに違反がある場合は、その違反も今回の再編対象に含める。
- 既存コードの流用可否は、動作有無ではなく規約適合性で決める。
- レビュー指摘を受けて修正するときは、指摘箇所だけでなく、その修正変更セット全体を対象に、各レビュー担当の観点から同種の欠陥、責務混在、参照不整合、証跡不足、導線欠落、状態遷移不備が残っていないかを確認し、残っているものは同一修正で解消しなければならない。
- 指摘箇所だけを直し、同一変更セット内に見えている未解消欠陥を残したまま修正完了扱いにしてはならない。
- 欠陥が構造、責務境界、記録構造、参照フローに関係する場合、欠陥原因となる構造単位を必ず再設計対象に含め、欠陥クラスが消えるまで実装・文書を再構成しなければならない。

## 記録義務

- 確認証跡には、確認対象差分識別子・実行コマンド・結果・未実施理由（ある場合）を記録する。
- 実装差分がない場合は、`実装` と `文書整合` を分離して記録し、`コード差分なし` を明示する。
- `状態: 未開始` かつ `主成果物: 実コード差分` の作業項目では、完了条件・`規約違反の解消対象`・`構造完了条件` に対する現行コード追跡結果を、確認可能な形で確認証跡または実装記録へ残す。

## 完了・継続義務

- 編集や広範検証の前に、適用される指示を特定し、その制約内で実装する。
- 親オーケストレーターによる委譲の完了後は、委譲内容の実装完遂が優先される。実装担当は「まず `/orchestration` を再起動する」「main agent として subworker を再度 spawn する」といった行動で delegated task の実行を停止してはならない。
- コード変更では、完了前に差分をコードスタイル規則で確認する。formatter、lint、test の成功を指示遵守の代替にしてはならない。
- 割り当て作業が許可されたスコープ内で実際に完了する前に最終応答を送ってはならない。
- 割り当て作業が未完了のまま、短文や簡易回答を進行停止の手段として使ってはならない。
- 割り当てられた是正項目または作業項目が完了するまで実行を継続する。継続不能な実制約がある場合のみ、その制約を利用者へ明示して停止する。

## 検証選択

- 変更対象に関係する検証だけを選ぶ。変更を検証しない広範チェックを機械的に実行してはならない。
- Markdown のみの変更では、生成文書や記載コマンド検証に関係する場合、または利用者が明示要求した場合を除き、`cargo xtask check` / `cargo xtask check static` を実行しない。代わりに `git diff --check`、必要な表示確認、変更リンク先確認を行う。
- コード、Nix、shell、workflow、bootstrap、生成物の変更では既定検証（`cargo xtask check`）を実行する。
- 成功済み検証は、差分変更後・最終差分未網羅・利用者再実行要求のいずれかがある場合のみ再実行する。`git status` / `git diff` など読み取り専用確認は再実行理由にならない。
- 検証は必ず flake dev shell から実行する。dev shell 外なら `direnv exec .` を前置する。
- zsh 設定・起動挙動・TAB バインド・fzf-tab・autosuggestions・syntax highlighting・PATH 処理に影響する変更では `cargo xtask check zsh` を実行する。
- bootstrap・初回実行・ホスト切替・マシン横断前提に影響する変更では `cargo xtask check runtime` を実行する。runtime チェックには dev shell の Darwin VM ツール群（Tart/Packer/Ansible）が必要である。
- 検証コマンドの一覧と用途は `README.md` の「検証」節を参照する。静的チェック詳細は `rust/tests/checks/src/static_checks.rs`、zsh 不変条件は `rust/tests/checks/src/zsh.rs` を参照する。

## ローカル生成物の取り扱い

- リポジトリ外の生成済み dotfiles やマシン固有 dotfiles を手編集してはならない。正本はこのリポジトリと `~/.config/dotfiles` に生成されるローカル flake である。
- 開発者の実 `~/.config/dotfiles` に書き込んでローカル flake 生成を手動検証してはならない。新規マシン相当や対象パス挙動は、リポジトリのサンドボックス検証、とくに実行時テストで確認する。

## 禁止

- 規約違反を「後で直す前提」で残したまま実装完了扱いにすること。
- 上記の再読対象を読まずに再編方針を決めること。
- 既存コードの責務混在を、互換性や作業量だけを理由に維持すること。
- 差分最小化や既存構造温存を優先して、規約適合に必要な再設計を回避すること。
- レビュー差戻しで示された指摘箇所だけを直し、同一変更セット内に見えている未解消欠陥を残すこと。
