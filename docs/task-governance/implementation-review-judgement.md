# 実装レビュー判定

この文書は、必須レビュー担当、判定表示、集約条件を定義する。

## 必須レビュー担当

- 実装差分（executable behavior を含む変更）:
  - `構造レビュー担当`
  - `セキュリティレビュー担当`
  - `仕様適合レビュー担当`
- 文書是正・文書主成果物:
  - `仕様適合レビュー担当`
- `AGENTS*`、`CLAUDE.md`、`.agents/skills/`、`docs/task-governance/`、`docs/architecture/`、`docs/` 配下のその他の規約文書（`docs/docs-governance.md` および各領域の運用規約・ゲート条件を定める文書）、`rust/tests/checks/`、`.github/workflows/`、`rust/xtask/src/ci/`、`rust/xtask/src/hook.rs`、`.claude/settings.json` を変更する場合、および高リスク変更を含む場合は `運用整合レビュー担当` を追加必須にする。

レビュー担当はこの 4 つで固定する。レビュー観点が足りないと感じても、新しいレビュー役割・判定段階・専任確認を追加してはならない。既存担当の職責として扱うか、指摘を不採用にすることで解決する。

## 各レビュー担当の職責

### 構造レビュー担当

[../architecture/hexagonal-implementation-rules.md](../architecture/hexagonal-implementation-rules.md) に従い、層別責務、依存方向、公開範囲、処理単位の責務配置、doc comment 規則、test double / fixture の配置を判定する。判定は形式（ファイル名、公開面の有無、`#[cfg(test)]` か `#[cfg(feature)]` か）ではなく責務で行い、機械的分離を合格根拠にしない。

### 仕様適合レビュー担当

ユーザー指定の GitHub issue / PR / 明示タスク、および領域固有仕様が定める完了条件、制約、是正対象を現行差分に対して直接照合する。テストが完了条件を実際に検証しているか、文書の参照が解決するかもこの職責に含める。サマリーや実装担当の報告で代替してはならない。

### セキュリティレビュー担当

[security-obligations.md](security-obligations.md) に定義された制約を適用し、秘密情報漏えい、不正アクセス経路、権限境界逸脱、危険な失敗時挙動を確認する。

### 運用整合レビュー担当

実行手順、gate 条件、CI 配線、完了判定への接続が実運用で強制可能かを確認する。規約文書が対象の場合は、[../docs-governance.md](../docs-governance.md) の「規約と検査の追加条件」に照らして、その規約が強制機構を持つか、維持費が便益に見合うかを判定する。補助記録の exact 同期不足だけを不合格根拠にしてはならない。

## レビュー開始条件

- 対象差分識別子がある。
- 比較範囲またはレビュー対象が固定されている。
- 必須レビュー担当が割り当て済みである。

文書是正・文書主成果物では、exact tracked-file set、file-count、補助記録の完全同期を開始条件にしない。

## 判定表示規則

- 各レビュー担当の返答は、先頭に `判定: <合格|要修正|不合格>` を 1 行で記録する。
- `判定` に使ってよいラベルは `合格`、`要修正`、`不合格` のみ。
- `判定要約: ...` を続け、`合格` の場合は `所見なし`、それ以外は主要論点を要約する。
- `根拠:` 見出しと箇条書きで判定根拠を記録する。
- 集約判定も `集約後レビュー判定: <合格|要修正|不合格>`、`集約判定要約: ...`、`集約根拠:` の順に揃える。

## レビュー独立性規則

レビュー担当は、過去のレビュー記録、確認記録、実装担当の報告を判定の代替にしてはならない。対象コード、対象文書、指定 issue / PR / タスクを直接読んで独立に判定する。

差し戻しで再実装を委譲する際、オーケストレーターは未解消 finding ごとに `reviewer role`、`verdict`、`file:line references`、`required fix` を handoff する。

## 集約規則

- 集約は、必須レビュー担当を兼務しない `レビュー集約担当` が行う。
- 1件でも `不合格` があれば未完了。
- `要修正` があれば修正後に再レビュー。
- 必須担当が全員 `合格` の場合のみ `集約後レビュー判定: 合格`。
- `要修正` 以上にできるのは、対象差分の中に具体的な欠陥（完了条件の未充足、規約違反、セキュリティ問題、誤動作）を file:line で指摘できる場合に限る。残留リスクの言及、将来の懸念、追跡したい事項、より良い設計の提案は finding として記録してよいが、それだけを理由に `要修正` にしてはならない。
- 前サイクルで解消のために新設された成果物そのものを対象にした指摘は、その成果物を削除して元の指摘を不採用にする方向でも解決してよい。
- 同一箇所への指摘が記述・文言の精度のみで 2 巡した場合、3 巡目の修正を委譲せず、その記述を残す価値を判定する。強制機構を持たない記述は削除して指摘を解決する。別文書への移設は削除に当たらない。

## コミット連動規則

- コミット関連作業は `集約後レビュー判定: 合格` の記録後に限り開始できる。
- 個別メッセージやチャット上の宣言のみで完了扱いにしてはならない。
