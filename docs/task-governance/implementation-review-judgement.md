# 実装レビュー判定

この文書は、レビュー開始条件・集約条件・完了判定への接続を定義する。

レビューサイクルは次の3段階に分離する。

1. **レビュー開始**（`S1 -> S2`）: 差分識別子と確認記録の存在確認、必須担当の割当。
2. **集約**（`S2 -> S3`）: 必須担当の全判定収集、集約後レビュー判定の確定。
3. **完了判定への接続**（`S3 -> S4`）: 集約判定 `合格` を前提に、コミット着手条件と完了判定担当への引き渡しを確認する。

各段階は独立した記録を持ち、前段が確定しない限り次段へ進んではならない。

## 用途

- 対象差分のレビュー開始可否を判定する。
- 複数レビュー結果を集約して最終判定する。
- 集約完了から完了判定担当への引き渡し条件を明確にする。

## 必須レビュー担当

- 実装差分（executable behavior を含む変更）:
  - `構造レビュー担当`
  - `運用整合レビュー担当`
  - `セキュリティレビュー担当`
  - `仕様適合レビュー担当`
- 文書是正・文書主成果物:
  - `運用整合レビュー担当`
  - `参照整合レビュー担当`
- 追加で高リスク変更を含む場合は `セキュリティレビュー担当` を必須化する。

## 各レビュー担当の職責

### 構造レビュー担当

`docs/architecture/hexagonal-implementation-rules.md` の層別責務・依存方向・公開範囲規則を適用する。主たる義務は `docs/architecture/review-checklist.md` の「レビュー時の問い」を各層についてコードを読む前に適用することである。問いへの答えが「哲学に違反している」であれば、チェックリスト項目が通過していても `判定: 不合格` とする。層別哲学的問いへの回答を `根拠:` に明示すること。見た目の構造（ファイル配置・命名）が正しくても実装の責務が層の哲学に反している場合は `判定: 不合格` とする。

### 仕様適合レビュー担当

作業定義文書の `規約違反の解消対象`・`構造完了条件`・`完了条件` を現行コードに対して直接照合する。各項目について現行コードを開いて未解消が残っていないかを確認する。サマリーや実装担当の報告で代替してはならない。

### セキュリティレビュー担当

`docs/task-governance/security-obligations.md` に定義された制約を適用する。機密情報の露出・不正アクセス経路・権限昇格の可能性を確認する。

### 運用整合レビュー担当

実行手順・役割分離・ゲート条件・証跡要件・完了判定ロジックの実運用での強制可能性・監査可能性を確認する。強制可能性・監査可能性に具体的懸念がある状態で `合格` としてはならない。

### 参照整合レビュー担当（文書是正専用）

文書内のリンク・参照先・ファイルパス・定義の一貫性を確認する。参照先が存在しない・定義と参照が不一致の場合は `判定: 不合格` とする。

`docs/docs-governance.md` が存在する場合は、対象文書がその文書規約に適合しているかを確認する。

対象がスキルファイル（`SKILL.md`）の場合は、以下を追加で確認する:

- frontmatter に `name` および `description` フィールドが存在し、内容がスキルの実態と整合していること
- `Required Reading Order` が存在し、スキルの実行に必要な参照元が欠落なく列挙されていること
- 正本複製禁止規則（governing source の内容をスキルファイル内に複製してはならない旨の規則）に適合していること

## レビュー開始条件

- 対象差分識別子がある。
- 最低1件の確認記録がある。
- 必須レビュー担当が割り当て済みである。
- 起動不能役割がある場合は、その事実と扱いをレビュー記録または領域規約が指定する記録先へ残す。
- 文書是正・文書主成果物のレビュー記録では、exact tracked-file set や file-count の列挙を開始条件にしてはならない。記録対象は、レビューした変更内容の要約、参照した確認記録、返却 verdict で足りる。

## 判定表示規則

- 各レビュー担当の返答は、先頭に必ず `判定: <合格|要修正|不合格>` を 1 行で記録する。
- `判定` に使ってよいラベルは `合格`、`要修正`、`不合格` のみとする。
- `通しません`、`No findings`、`指摘なし`、`no blockers`、`pass` などの自由文は判定ラベルの代わりに使ってはならない。
- `判定` の次に、必ず `判定要約: ...` を 1 行で記録する。
- `判定要約` は、`合格` の場合は `所見なし`、`要修正` または `不合格` の場合は差戻し理由または主要論点の要約とする。
- `判定要約` の次に、必ず `根拠:` 見出しと箇条書きで判定根拠を記録する。
- 集約判定も同じ構造で記録し、`集約後レビュー判定: <合格|要修正|不合格>`、`集約判定要約: ...`、`集約根拠:` の順に揃える。

## レビュー独立性規則

レビュー担当は過去のレビュー記録・確認記録・実装担当の報告を参照して判定の代替にしてはならない。判定は必ず対象コードを直接読んで独立に行わなければならない。過去サイクルの記録が合格であっても、現行コードを自分で確認せずに合格を返してはならない。既存のレビュー記録の存在は、実コード精査を省略する根拠にならない。

## 集約規則

- 1件でも `不合格` があれば未完了。
- `要修正` があれば修正後に再レビュー。
- 必須担当が全員 `合格` の場合のみ `集約後レビュー判定: 合格`。
- 差分が文書上/構造上は整合していても、必須の実行手順・役割分離・ゲート条件・証跡要件・完了判定ロジックについて、実運用での強制可能性または監査可能性に具体的懸念がある場合、レビュー担当は必ず所見を起票しなければならない。強制可能性/監査可能性が不確実な状態のまま `合格` としてはならず、`スコープ外` や `運用徹底` を理由に懸念を格下げしてはならない。
- 具体的懸念、残留リスク、未解消疑義、要追跡事項、運用依存の注意事項を記録したレビューは、すべて `finding あり` と扱う。これらを記録しながら `No findings`、`指摘なし`、`懸念なし`、または `合格` を併記してはならない。
- 前項に該当する記録が1件でもある場合、当該レビュー担当判定は少なくとも `要修正` とし、懸念の解消条件または差戻し事項を同一記録内に明記しなければならない。
- 必須レビュー担当のいずれかに `finding あり` の記録が残る場合、`集約後レビュー判定: 合格` にしてはならない。
- `主成果物: 実コード差分` の作業項目で `集約後レビュー判定: 合格` とする場合、合否判定を要約だけで決めてはならない。作業定義文書の `規約違反の解消対象` と `構造完了条件` に対し、現行コード追跡で未解消項目が残っていないことを確認できる場合に限り `合格` とできる。

## コミット連動規則

- コミット関連作業は `集約後レビュー判定` の記録後に開始できる。
- 個別メッセージやチャット上の宣言のみで完了扱いにしてはならない。
