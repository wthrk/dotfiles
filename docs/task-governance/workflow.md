# タスク運用ワークフロー

この文書は、リポジトリ全体で共有するタスク運用の進め方を定義する。

## 役割

- `オーケストレーター`: 現在の作業項目、参照すべきタスクファイル、着手順序、担当割当、フォールバック有無を確定し、進行順を制御する。distinct な実装担当、レビュー担当、進捗判定担当を実行できる間は、自分で対象差分を作ってはならない。進捗集約や前進記録は、進捗判定担当を兼務する明示的フォールバック記録がない限り行ってはならない。
- `実装担当`: [implementation-execution.md](implementation-execution.md#実装実行規則) の強制義務に従い、主成果物の差分、確認証跡、必要最小限の整合文書を作る。
- `進捗判定担当`: タスクファイルと粗粒度進捗の状態更新を行う。証跡が揃う前に前進させてはならない。
- `履歴復元担当`: 失われた issue / phase 進捗、旧タスク階層、過去の milestone を git 履歴やログから復元する。
- `タスク定義整備担当`: タスク本文だけでは仕事の内容が分からない場合に、作業定義文書の分割、参照張替え、重複除去を行う。

## サブエージェント割当規則

- コンテキスト最小化のため、役割または作業項目が変わるたびに新しいサブエージェントを割り当てる。
- 1 つのサブエージェントを、異なる作業項目へ再利用してはならない。
- 1 つのサブエージェントを、`実装` / `レビュー` / `進捗判定` / `履歴復元` / `タスク定義整備` の異なる役割へ転用してはならない。

## 複数レビュアー規則

- レビューは 1 人で閉じてはならない。少なくとも 2 人以上のレビュー担当を起動し、それぞれ異なる確認責務を割り当てる。
- レビュー担当の役割は、最低でも次の 2 系統に分ける。
  - `構造レビュー担当`: 責務境界、依存方向、公開インターフェース境界、アーキテクチャ適合を確認する。
  - `運用整合レビュー担当`: 状態遷移、証跡、開始条件、台帳更新、履歴復元、参照整合を確認する。
- 実装差分では、さらに次の確認責務を追加しなければならない。
  - `セキュリティレビュー担当`: 秘密値、認証情報、権限境界、永続化、ログ、外部入出力、危険な失敗時挙動を確認する。
  - `仕様適合レビュー担当`: 仕様書、設計書、作業定義文書に対して、要求挙動と停止条件が正しく実装されているか確認する。
- 文書構成変更、タスク運用変更、スキル変更、`AGENTS.md` 変更のいずれかを含む場合は、さらに `参照整合レビュー担当` を追加する。

## 開始条件

作業開始前に、少なくとも次を同一作業項目内で追跡可能に確定する。

- `現在の作業項目`
- `実装担当`
- `構造レビュー担当`
- `運用整合レビュー担当`
- `セキュリティレビュー担当`
- `仕様適合レビュー担当`
- `進捗判定担当`
- `実装担当 agent/run` 識別子
- 各レビュー担当の `agent/run` 識別子
- `進捗判定担当 agent/run` 識別子
- `着手順序`
- `役割別フォールバック記録`（フォールバックがある場合は必須。`対象役割`、`起動失敗理由`、`起動失敗証跡`、`代替実行者`、`代替実行者 agent/run 識別子`、`no-reuse 規則充足根拠` を同一記録で保持）
- `現行対象再読確認`

いずれかが未確定のまま実装やレビューへ入ってはならない。

## 進め方

1. オーケストレーターはタスクファイル、対応する作業定義文書、必要なら粗粒度進捗文書を特定する。
2. 仕事の内容が不明瞭なら、先に `履歴復元担当` または `タスク定義整備担当` を割り当てる。
3. 実装担当は [implementation-execution.md](implementation-execution.md#実装実行規則) に従って再読し、主成果物を作成する。
4. 実装担当は確認を行い、追試可能な証跡を残す。
5. オーケストレーターは複数レビュー担当を起動し、役割ごとに対象範囲を分割する。
6. 各レビュー担当は、自分の役割範囲で差分と証跡を確認し、所見を返す。
7. 進捗判定担当のみが、複数レビュー担当の結果を集約する。オーケストレーターが兼務する場合は、明示的フォールバック記録を同一変更セットへ残す。
8. 進捗判定担当は、証跡が揃った変更セットだけを前進反映する。

## フォールバック

役割を分離できない環境では、オーケストレーターは停止せず、起動できない役割ごとに代替実行者を明示してフォールバックさせる。フォールバック宣言前に、オーケストレーターのまま対象差分を作ってはならない。

- フォールバックは役割単位で記録し、`フォールバック有無` だけの記録で済ませてはならない。
- 各フォールバック記録には、`対象役割`、`起動失敗理由`、`起動失敗証跡`、`代替実行者`、`代替実行者 agent/run 識別子`、`no-reuse 規則充足根拠` の6項目を必須で残す。
- `レビュー` では、必須レビュー役割ごとに起動またはフォールバックのどちらかを成立させ、未成立の役割が残る状態で開始してはならない。

## 再開時の扱い

作業再開時は、前回の計画や古い進捗記録だけを根拠に実装へ直行してはならない。実装担当は対象コードまたは対象文書を再読し、再読確認を次回着手前記録へ残す。
