# タスク運用ワークフロー

この文書は、リポジトリ全体で共有する最小限のタスク運用フローを定義する。

## 1. 目的

- 作業の制御に必要な最小項目だけを統一する。
- 主な必須記録は `変更差分`、`レビュー結果`、`コミット連動判定` とする。
- 同じ事実を複数台帳へ重複同期する運用を必須にしない。
- 後付けの文書書換えだけで満たせる形式 gate / contract / branch condition は導入しない。実行、レビュー品質、検証正確性を実質的に改善しない exact file-set/file-count、重複 scope ledger、actor/run bookkeeping などは必須条件にしない。

## 2. 役割

- `オーケストレーター`: 対象作業と担当を確定し、進行を制御する。
- `実装担当`: 差分を作成し、必要な確認を行う。
- `レビュー担当`: 役割別観点で判定を返す。
- `進捗判定担当`: レビュー結果に基づいて進捗更新要否を判断する。
- `完了判定担当`: 完了条件と残課題を判定する。

オーケストレーターは、active work item の選定、担当割当、記録更新だけを扱う。オーケストレーション進行中、現在の実行者はオーケストレーター役割に拘束され、ファイル直接編集、実装作業の直接実行、レビュー判定/進捗判定/完了判定の直接実施をしてはならない。実装十分性判定、規約適合判定、完了判定を自分で行ってはならず、それらは対応する担当役割へ委譲する。
タスク実行依頼（進行/継続/完了系指示を含む）は、必ずオーケストレーションから開始する。active work item 選定後、オーケストレーターが実行できる行為は「必要役割の起動」または「起動/利用失敗の最小記録」のみであり、追加の自己判断作業へ進んではならない。利用者依頼がすでにタスク実行コマンドである場合、委譲可否の追加許可を利用者へ求めてはならない。タスク実行依頼を受けた時点で、オーケストレーターは利用者の追加許可を待たずに自律的に必要役割のサブエージェントを起動しなければならない。委譲の実行は義務であり、「明示された委譲要求がない」という理由でサブエージェント起動を遅延・回避してはならない。
役割起動の成功/失敗処理が確定するまで、オーケストレーターは実装判定目的で対象コード/仕様/テスト/レビュー成果物を読んではならず、テスト実行およびファイル編集も禁止する。

## 3. 最小状態

- `S0: 開始待ち`
- `S1: 実装中`
- `S2: レビュー中`
- `S3: レビュー集約完了`
- `S4: コミット着手可`

進捗判定の基本状態との対応は次のとおり。

- `未開始` = `S0`
- `進行中` = `S1` / `S2` / `S3`
- `S4` は `コミット関連作業を開始できる状態` を表し、作業項目の `完了` 判定そのものは表さない。

## 4. 基本フロー

1. `S0 -> S1`
   - 対象作業と担当を決める。
   - オーケストレーターは `docs/tasks/tasks.md` で `現在の作業項目` を先に読み、該当項目の `状態`、`主成果物`、`対象コードパス/対象文書パス`、`作業定義文書`、`レビュー記録` の順で確認して active work item を 1 件確定する。
   - active item 選定段階の読み取りは、上記フィールド値の取得と参照先の存在確認に限定する。作業定義文書とレビュー記録の本文を読んで内容判断してはならない。
   - active work item の確定後、オーケストレーターは実装担当・レビュー担当・進捗判定担当（必要時は完了判定担当）へ作業を委譲し、自分でファイル直接編集・実装・レビュー・進捗判定・完了判定を代行しない。
   - active work item 確定直後のオーケストレーター実行は、必要役割の起動、または役割起動/利用失敗時の最小記録の残置に限定する。起動成功/失敗が確定する前に、実装判定のための対象コード/仕様/テスト/レビュー成果物の読み取り、テスト実行、ファイル編集を行ってはならない。
   - `完了させる`、`全部やる`、`進める` 等の依頼でも、まず root active ledger（`docs/tasks/tasks.md`）で現在の active work item を 1 件確定し、その項目が要求する領域資料（`docs/tasks/<area>/tasks.md` 参照を含む）を読む。台帳で未選定の他項目やブランチ差分全体を一括完了対象として扱ってはならない。
   - `work-item-governed` か `task-list-outside` かを判定する。
   - `task-list-outside` の場合は、`docs/task-governance/review-artifacts/outside-ledger-intake.md` に分類と責任境界の最小記録を残してから進む。
2. `S1 -> S2`
   - 実装担当が変更差分を作成し、必要な確認を記録する。
   - 実装方針の厳格規則は、共通規約では再定義せず、`implementation-execution.md` と各領域の `implementation-guidelines.md` を正本として適用する。
   - オーケストレーターは、ブランチ差分、既存コミット、テスト通過のみを根拠に `追加実装不要` や `完了可能` を自分で判断してはならない。
3. `S2 -> S3`
   - 必須レビュー役割の判定を集約し、`合格` / `要修正` / `不合格` を確定する。
4. `S3 -> S4`
   - コミット着手条件を満たす場合のみ進む。
   - active work item が完了したら、次回実行前に root active ledger（`docs/tasks/tasks.md`）の `現在の作業項目` を次の未完了項目へ進める。

`要修正` または `不合格` がある場合は `S1` に戻る。

## 5. 記録先

- `work-item-governed`
  - active work item の選定: `docs/tasks/tasks.md`
  - active work item が参照する領域台帳/履歴: `docs/tasks/<area>/tasks.md`（active 選定の正本ではない）
  - レビュー記録: `docs/tasks/<area>/review-artifacts/*.md`
- `task-list-outside`
  - 着手前判定とレビュー記録: `docs/task-governance/review-artifacts/*.md`

`documentation-remediation` では、無関係な `tasks.md` / `issue-*.md` の同時同期を必須にしない。

### サイクル分離

- 同一作業項目の記録は **current-cycle** と **過去サイクル** を分けて管理する。
- `docs/tasks/<area>/tasks.md` の作業項目エントリには、現行サイクルの確認/レビュー記録パスを `現行サイクル確認/レビュー記録（<日付>）` フィールドとして記載し、完了済みサイクルの記録は `履歴レビュー記録（<日付>）` フィールドへ移す。
- 現行サイクル記録と履歴記録を同一フィールドに混在させてはならない。オーケストレーターは active item 選定時に現行サイクルの記録パスのみを参照し、過去サイクルの記録を読んで内容判断してはならない。

## 6. コミット着手ゲート

コミット関連作業の開始条件は次のとおり。

- 対象差分が特定できる。
- 必要レビュー役割の結果が記録され、集約後レビュー判定が `合格`。
- チャットや口頭報告のみを根拠にしていない。
- 領域固有文書がより厳格な条件を定める場合は、その条件を満たしている。
- 文書是正の記録は、厳密な tracked-file 数や exact file-set 列挙を commit/review gate にしてはならない。最小記録は「何の変更を確認/レビューしたか」「何の確認を実行したか」「どの判定が返ったか」とする。

文書是正では、レビュー記録を主記録とし、粗粒度進捗同期は任意とする。

## 7. 役割分離

- 役割分離は維持する。
- subagent は異なる作業項目間・異なる役割間・同一作業項目の異なるサイクル間のいずれにおいても再利用してはならない。各役割起動は fresh agent でなければならない。
- オーケストレーターは自己実行（self-execution）を行ってはならない。実装・レビュー・進捗判定・完了判定のいずれも自分で代行せず、必ず対応役割の fresh subagent へ委譲する。
- fresh agent の起動が上限で失敗した場合は、まず完了済み subagent を閉じて fresh agent の再起動を試みる。
- 起動数制限や thread limit は、割当済み subagent の再利用理由にならない。
- 必須役割を起動できない場合は、その事実と扱いを対象レビュー記録または領域規約が指定する記録先へ残す。
- ツールが `don't ask mode` によりブロックされ、必要な操作が物理的に実行できない場合、オーケストレーターは自己判断で代替手段を試みてはならない。その事実と未実行の理由を利用者へ直接報告し、権限付与または代替指示を求める。ブロックの報告は、ツール呼び出しを実際に試みた後にのみ行う。「ブロックされているはず」という推測のみを根拠に呼び出しを省略して報告してはならない。
- 実装差分や高リスク変更で要求される複数レビュー役割は省略しない。
- 「フォーマット修正のみ」「stub 追加のみ」「コメント修正のみ」等、変更が軽微であるという理由はオーケストレーターの自己実行を正当化しない。軽微な変更であっても実装・コミットは実装担当 subagent へ委譲しなければならない。
- subagent への委譲は、1 回の起動で完走可能な粒度に分割して行う。複数作業項目・複数バージョン・広範囲ファイル群を一括で単一 subagent に委譲してはならない。委譲粒度が大きすぎてセッション内で完走できなかった場合、オーケストレーターはその委譲設計の失敗として記録し、次回起動では粒度を縮小して再委譲する。
- subagent の起動・実行が失敗した場合、同一指示を原因分析なしに再実行してはならない。失敗の原因（ツールブロック・粒度超過・依存未解決・指示曖昧 等）を特定し、原因に対応した修正を加えた上で再委譲する。
- コミット前に `adapters/` 配下の全ファイルの公開面（`pub`・`pub(crate)`・`pub(super)` を含む）を確認し、port trait を実装する型・メソッド以外が外部に公開されていないことを検証する。この確認をレビュー担当 subagent の判定で代替してはならない。アーキテクチャ違反が残るコミットは無効とし、差し戻してから再実装を委譲する。
- パーミッションエラーが発生した場合、パーミッション設定の変更を試みてはならない。許可されているパターンに合うコマンド形式を探し、対応するコマンドで代替する。代替が不可能な場合のみ、その事実を利用者へ報告する。
- Codex 等のサブエージェントが sandbox 制約によりコミットを実行できない場合でも、オーケストレーターがコミットを代行する前に `implementation-review-judgement.md` に定められた全必須レビュー役割（構造レビュー・仕様適合レビュー・セキュリティレビュー・運用整合レビュー）の全員合格を集約済みでなければならない。代行可否はサブエージェントの実行能力の問題であり、レビューゲートの省略理由にはならない。
- `cargo check` の合格・テストの通過・ビルド成功はレビュー合格の代替にならない。必須レビュー役割が判定していない限り、コミット着手条件を満たさない。
