# docs 文書運用規約

この文書は `docs/` 配下の配置、正本、重複禁止に加え、規約・検査コード・レビュー役割を追加してよい条件を定義する。

## 配置規則

- `docs/README.md`: 恒久文書全体の入口。
- `docs/task-governance/README.md`: 共通タスク運用規約の入口。
- `docs/architecture/README.md`: アーキテクチャ規約の入口。
- `docs/<area>/README.md`: 領域仕様・設計文書の入口。

作業台帳、完了済み work item、確認記録、レビュー記録、issue progress、current-cycle 記録は恒久文書ではない。必要な履歴は GitHub issue / PR / git history で追跡し、repo 内 docs に再掲しない。

## 正本規則

- 共通運用規約は `docs/task-governance/` に置く。
- アーキテクチャ規約は `docs/architecture/` に置く。
- secret-recovery の仕様・設計・runbook・secret handling は `docs/secret-recovery/` に置く。
- 役割スキルの初動・担当境界は `.agents/skills/*/SKILL.md` に置く。
- ユーザー指定の GitHub issue、PR、または明示タスクが作業単位であり、repo 内 task ledger を正本にしない。

## 記載規則

- README は導線だけを記載し、本文規約を再掲しない。
- 仕様・設計・運用規約・作業履歴の責務を混在させない。
- 正本が所有する規則を別文書へ長文再掲しない。必要な場合は正本への参照にする。
- 後付けの文書書換えだけで充足できる形式要件を gate にしてはならない。
- exact file-set、file-count、actor/run bookkeeping、current-cycle 文言、補助記録の完全同期は review gate / commit gate / PR 対応義務の代替にしない。
- PR review comment への採用/不採用返信と resolved 状態の維持は、補助記録同期とは別の実作業義務として扱う。

## 規約と検査の追加条件

規約文書、検査コード（静的検査・テスト・CI ゲート）、レビュー役割、判定段階、記録義務は、次のいずれかを満たす場合に限り追加してよい。

- 実際に発生したインシデント、障害、または再現した欠陥に紐づいている。
- 機械的な強制機構（静的検査、テスト、CI ゲート、型、リンタ）を伴い、その維持費が防ぐ失敗の費用に見合う。

次は追加してはならない。

- 強制機構を持たず、レビュー作業を生むだけの規約。追加したい規則を機械で強制できないなら、規約にしない。
- 他の正本、言語仕様、リンタ、型システム、既存ツールが既に保証していることの再掲。
- 発生したことがなく、実インシデントに紐づかない失敗モードを守るための検査コードと、そのためのテスト。
- 新しいレビュー役割、判定段階、コミット直前の専任確認、記録同期義務。
- **リポジトリ自身のソーステキストを解析する検査**。workflow YAML の step 名や実行行の grep、Nix ソースの
  マーカー抽出、Rust 定数の配列リテラルの読み取り、生成された script 本文の解析はいずれもこれに当たる。
  アンカーは rename で壊れ、手書きの写しは保守だけを増やし、記述が変わっただけで落ちる。検査してよいのは
  **評価値と実行結果**だけである。
- 定数表や宣言をもう一方の場所へ手で写し、両者の一致を検査で担保する構成。写しを作らず、一方を他方から
  導出するか、片方を消す。
- **自分が今書いた宣言をそのまま読み返すだけの検査**。手書き定数の重複や要素数のように、宣言を見れば分かり、
  実際に起きたことのない事象を対象にするものが該当する。防ぎたい状態があるなら、検査を足すのではなく
  それを表現できない型・データ構造にする。

静的検査に置いてよいのは、標準のリンター（`cargo fmt` / `clippy` / `test`、`actionlint`、`bash -n`、
`nix fmt`、`nil`、`nix flake check`）と、**リンターが評価しない構成の評価**だけである。それ以外を足したく
なった場合は、まず実行して確かめる経路（実環境での適用と起動）に寄せられないかを検討する。

**レビュー finding を解消する目的だけで、新規文書・新規検査・新規役割を作ってはならない。** finding は、既存正本への追記、既存検査の修正、または指摘の不採用のいずれかで解決する。前サイクルの finding を解消するために新設された成果物が次サイクルの finding を生んでいる場合は、その成果物を削除して元の指摘を不採用にする。

## 参照規則

- 参照は存在する恒久文書、コードパス、または外部の GitHub issue / PR へ向ける。
- 削除済みの作業管理文書へリンクしない。
- 正本を移す場合は旧記述を削除または参照化し、二重正本を残さない。
