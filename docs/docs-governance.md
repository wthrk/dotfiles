# docs 文書運用規約

この文書は `docs/` 配下の配置、正本、重複禁止を定義する。

## 配置規則

- `docs/README.md`: 恒久文書全体の入口。
- `docs/task-governance/README.md`: 共通タスク運用規約の入口。
- `docs/architecture/README.md`: アーキテクチャ規約の入口。
- `docs/<area>/README.md`: 領域仕様・設計文書の入口。

作業台帳、完了済み work item、確認記録、レビュー記録、issue progress、current-cycle 記録は恒久文書ではない。必要な履歴は GitHub issue / PR / git history で追跡し、repo 内 docs に再掲しない。

## 正本規則

- 共通運用規約は `docs/task-governance/` に置く。
- アーキテクチャ規約は `docs/architecture/` に置く。
- secret-recovery の仕様・設計・runbook・secret handling は `docs/secret-recovery/` に置く。
- 役割スキルの初動・担当境界は `.agents/skills/*/SKILL.md` に置く。
- ユーザー指定の GitHub issue、PR、または明示タスクが作業単位であり、repo 内 task ledger を正本にしない。

## 記載規則

- README は導線だけを記載し、本文規約を再掲しない。
- 仕様・設計・運用規約・作業履歴の責務を混在させない。
- 正本が所有する規則を別文書へ長文再掲しない。必要な場合は正本への参照にする。
- 後付けの文書書換えだけで充足できる形式要件を gate にしてはならない。
- exact file-set、file-count、actor/run bookkeeping、current-cycle 文言、補助記録の完全同期は review gate / commit gate / PR 対応義務の代替にしない。
- PR review comment への採用/不採用返信と resolved 状態の維持は、補助記録同期とは別の実作業義務として扱う。
- 文書ファイル（.md を含む）の一括置換に Python スクリプト・sed スクリプトを使ってはならない。文書の変更は常に edit ツールで行う。
- 参照資料の直接照合は、この節を正本とする。

### 参照資料の直接照合

- 実装担当および各レビュー担当は、対象コード、テスト、コード doc comment、恒久文書、委譲入力に URL、リンク、引用、API symbol、仕様節、source location、またはそれらを根拠とする主張を見つけた場合、引用元の原文を自ら開いて読む。対象は repository 内の正本文書、外部仕様、vendor documentation、SDK / crate の公式資料・公式サンプル・versioned source を含む。URL の解決確認、見出し・symbol の存在確認、実装担当・過去レビューの要約、検索結果、又聞きだけで代替してはならない。
- 読む際は、主張と原文の対応、引用箇所の前後文脈と適用範囲、参照先の版・revision・公開状態、および対象の依存 version / 実装 / 仕様との対応を直接照合する。引用の一部だけを取り出して、原文が限定・例外・前提としている内容を落としてはならない。
- 原文を開けない、取得できない、版または適用範囲を照合できない場合、その URL、引用、または参照は根拠として採用してはならない。実装・レビュー記録では未読または取得不能であることを明記し、当該参照に依存する合格、エラー分類、状態遷移、または設計判断を行ってはならない。
- 外部 SDK / crate の利用根拠は、この節を正本とする。

### 外部 SDK / crate の利用根拠

### 基本設計から SDK 利用へ進む順序

- 実装担当および各レビュー担当は、実装・テスト・レビューの前に、まず作業単位を定めるユーザー指定 issue / PR / 明示タスクと対象領域の正本仕様・基本設計・runbook を直接読む。この段階で、少なくとも目的、対象 resource / secret、各値の generate → save → read → use → dispose、前提・成功・失敗時の状態遷移、利用者が入力・保持・出力してはならない値と破壊的操作の禁止を列挙して照合可能にする。
- 次に、その正本が求める操作を実現する手段として、SDK / crate / vendor の全体フロー文書、仕様、公式サンプル、API documentation、versioned source を直接読む。SDK の API 単体、サンプル、実機観測、既存実装は product の目的・storage target・状態遷移・禁止事項を置換、補完、または変更する根拠にはならない。
- 実装とレビューでは、前二段階で確定した product flow の全遷移（generate / save / read / use / dispose、入力、出力、失敗、cleanup）を、コード、テスト、doc comment、外部 SDK 呼び出しへ一つずつ照合する。正本設計が欠ける、または SDK 文書と矛盾する場合は推測で接続せず、根拠不足として停止して設計判断を要求する。
- 根拠を記載する code doc comment と恒久文書は、product flow を定める repository 正本と、それを実現する SDK / vendor の一次資料を区別して URL と位置を併記する。レビュー担当はその両方の原文を自ら開き、実装者の要約を根拠にしない。

- 適用対象は、repository-authored code が直接利用する**すべて**の外部 SDK / crate である。SDK と呼ばれる crate だけでなく、外部サービス、デバイス、OS、暗号、通信、永続化、認証の振る舞いを提供する crate を含む。依存の名称、対象機能、変更の有無で適用範囲を狭めてはならない。
- 実装担当と、対象差分を判定する各レビュー担当は、利用する API だけでなく、認証、入力・出力データモデル、初期化から終了・cleanup までの利用フロー、成功時・失敗時の状態遷移を、当該 SDK / crate または対象プロトコルの公式一次資料で直接確認する。一次資料は upstream が管理する API documentation、versioned source、仕様、または vendor documentation とする。引用、公式サンプル、API documentation、仕様節の扱いには [参照資料の直接照合](#参照資料の直接照合) を適用する。二次解説、検索要約、実機観測、エラー本文の文字列照合、推測は意味付けの根拠にならない。
- 呼び出す外部 API のエラー面を完全に確認し、外部 SDK / crate から得る**すべてのエラー値**（variant、error code、status、戻り値、または API が定義する失敗状態）を一次資料へ対応付ける。各値の意味、分類、当該 API で許される遷移を確認する。資料が個別値を定義しない場合は、その不定義性自体を根拠として記録し、当該値を opaque な失敗として一律に伝播する。retry、fallback、default 値化、空値化、別エラーへの写像、握りつぶし、成功扱い、状態の継続・初期化・削除を行う場合も、同じく一次資料の根拠を要する。
- 一次資料で意味または許容遷移を証明できない外部エラーを、存在しない資源、再試行可能、一時障害、認証失敗、既存状態、成功相当などと解釈してはならない。その場合は、元のエラーを文脈付きで伝播するか、根拠不足を明示した失敗として停止する。未確認の fallback、default、空値化、握りつぶし、状態変更は禁止する。
- 実装確認とレビュー判定では、利用した一次資料の URL と、API symbol、仕様節、または source path と行番号等の再現可能な位置を直接確認する。作業報告・レビュー根拠には、その URL と位置、およびそれが裏付ける利用フローまたはエラー判断を記す。repo 内にこのためだけの恒久的な補助台帳・確認記録を作成してはならない。

## 参照規則

- 参照は存在する恒久文書、コードパス、または外部の GitHub issue / PR へ向ける。
- 削除済みの作業管理文書へリンクしない。
- 正本を移す場合は旧記述を削除または参照化し、二重正本を残さない。
