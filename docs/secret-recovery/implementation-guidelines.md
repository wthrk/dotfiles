# 秘密情報復旧基盤の実装ガイドライン

この文書は、秘密情報復旧基盤で恒久的に参照する実装方針の正本である。計画依頼で使う固定実装単位、役割分担、実装時の境界を定義する。

## 目的と対象範囲

目的は、秘密情報復旧基盤の実装を一貫した層構造、秘密値の所有境界、成果物境界に固定し、secret-recovery 作業全体で同一の判断基準を維持することである。対象は `dotfiles secrets` のコマンドフロー、関連するドメインモデル、ワイヤ形式、ポート、アダプター、補助機能、設計文書である。

## 参照正本

一般構造の判断は [docs/architecture/hexagonal-implementation-rules.md](../architecture/hexagonal-implementation-rules.md) を参照する。機能仕様と保存仕様の判断は [secret-recovery-spec.md](secret-recovery-spec.md) と [yubikey-secret-storage-design.md](yubikey-secret-storage-design.md) を参照する。

## 計画依頼の固定実装単位

secret-recovery の計画実装で扱う実装単位は次の 6 つに固定する。

1. `規約計画`
2. `実装計画`
3. `規約文書更新`
4. `確認`
5. `レビュー`
6. `必要時の後続対応`

## オーケストレーション規約

secret-recovery の `規約計画`、`実装計画`、`規約文書更新`、`確認`、`レビュー`、`必要時の後続対応` を伴う依頼では、メインエージェントはオーケストレーション専任とする。メインエージェントは、適用規約確認、担当割当、依頼順序制御、差戻し先判断、利用者向け進捗報告だけを扱う。

メインエージェントは、担当役割に割り当てられた実作業を自分で実施してはならない。禁止対象には、repo 探索、コマンド実行、ファイル確認、差分確認、文書編集、検証実行、レビュー判定、レビュー証跡作成を含む。

## 計画・実装・レビューの役割分担

計画依頼で扱う作業者の役割は、実装担当とレビュー担当に固定する。役割ごとの実施可能範囲は次のとおり。

- 計画: 実装担当だけが `規約計画` と `実装計画` のための探索、判断、本文作成、更新を行う。レビュー担当は計画本文を編集せず、`レビュー` で合否判定を行う。メインエージェントは計画本文を作成・更新しない。
- 実装: 実装担当だけが `規約文書更新` と `必要時の後続対応` のための対象確認、差分作成、文書更新を実施する。レビュー担当は実装差分を直接編集せず、必要な差戻しを判定する。メインエージェントは実装差分を直接編集しない。
- 確認: 実装担当が `確認` のための確認観点抽出、検証実行、結果記録を実施する。レビュー担当は確認内容を再確認できる。メインエージェントは確認作業を直接実施しない。
- レビュー: レビュー担当だけが `レビュー` のための差分確認、証跡確認、合否判定を確定する。実装担当は差戻し時の再実施を担当する。メインエージェントはレビュー判定を直接実施しない。

## 進捗状態の判定規則

`docs/secret-recovery/tasks.md` の各作業項目は、固定実装単位（`規約計画` / `実装計画` / `規約文書更新` / `確認` / `レビュー` / `必要時の後続対応`）ごとに `状態`・`成果物`・`完了条件` を対応づけて管理する。

Phase/Issue レベルの完了判定は本節の判定規則を正本とし、`tasks.md` の作業項目 `状態` を単純集計して代替してはならない。

`docs/secret-recovery/tasks.md` の作業項目 `完了` は、対象作業項目で `規約文書更新` だけでなく `確認` と `レビュー` が完了し、必要時は `必要時の後続対応` まで終えたときにだけ設定する。仕様・設計・ガイドライン文書の更新完了だけで `完了` を設定してはならない。

進捗用語は次のとおり厳密に区別する。

- `文書整合完了`: 対象作業項目に必要な規約文書差分（`規約文書更新`）が整い、文書間の語彙・参照が整合している状態。
- `実装完了`: 対象作業項目の要求範囲に executable behavior が含まれる場合に、その挙動がコード差分として実装され、必要な `確認` と `レビュー` を通過した状態。

対象作業項目の要求範囲に executable behavior が含まれる場合、`規約文書更新` / `確認` / `レビュー` の完了だけを機能実装完了として解釈してはならない。機能完了の判定は `実装完了` の条件でのみ行う。

対象作業項目の要求範囲に executable behavior が含まれ、`実装状態` が `未実装` または `実装中` の間は、主実行対象をコード実装作業として扱う。固定実装単位トラッカー上で `規約文書更新` が未完了で残っていても、それだけを根拠に文書作業を `次のタスク` の主対象へ繰り上げてはならない。

## 実装単位ごとの実装方針

### `規約計画`

- 実装内容: 作業項目で適用する規約範囲、参照正本、除外範囲を確定する。
- 分割方針: 作業項目ごとに規約適用点を分け、他作業項目とは独立に扱う。
- 責務境界: 対象作業項目の規約適用範囲、参照正本、除外範囲の定義だけを扱う。
- 荒い受け入れ条件: 参照正本と適用範囲が衝突なく示される。

### `実装計画`

- 実装内容: 対象作業項目で更新する文書・節・成果物と更新順序を確定する。
- 分割方針: `規約文書更新` を作業項目単位で完結する差分に分ける。
- 責務境界: 対象作業項目の更新対象文書・節・成果物と更新順序の定義だけを扱う。
- 荒い受け入れ条件: 更新対象と順序が示される。

### `規約文書更新`

- 実装内容: 計画で確定した対象文書を更新し、語彙と参照を整合させる。
- 分割方針: 対象作業項目に必要な文書差分だけを扱う。
- 責務境界: 対象作業項目に必要な規約文書差分を扱う。
- 荒い受け入れ条件: 必要な文書更新が完了している。

### `確認`

- 実装内容: 更新後文書の整合を確認する。
- 分割方針: 確認対象は対象作業項目に必要な範囲に限定する。
- 責務境界: 対象作業項目に必要な確認だけを扱う。
- 証跡要件: 少なくとも (1) 対象差分の識別情報（コード差分がある場合はコード差分識別子を含む）、(2) 実施した確認手順（例: `git diff --check`、必要時のリンク確認）、(3) 手順ごとの結果、(4) 未実施項目がある場合の理由、を同一作業項目内で追跡可能な形で記録する。コード差分がない場合は `コード差分なし` を明記し、対象作業項目のスコープに照らした理由を併記する。
- 荒い受け入れ条件: レビュー担当が追試可能な確認証跡が揃っている。

### `レビュー`

- 実装内容: 変更差分をレビューし、差戻し有無を判定する。
- 分割方針: 判定は作業項目ごとに行い、不合格時は同じ作業項目で必要な単位を再実施する。
- 責務境界: 対象作業項目の差分に対する合否判定だけを扱う。
- 荒い受け入れ条件: 合格時は後続対応要否とコミット関連作業の着手可否が判定される。不合格時は再実施対象が示され、`レビュー` は未完了のままとする。

### `必要時の後続対応`

- 実装内容: レビュー合格後に必要と判定された最小限の追従更新とコミット関連作業の実施・委譲記録を行う。
- 分割方針: 後続対応が必要な作業項目だけを対象にする。
- 実施者境界: コミット関連作業の実施者と委譲方法は `AGENTS.md` の Commit Rules を正本として従い、この文書ではレビュー合格後に着手可能となるタイミングだけを定義する。
- 責務境界: 対象作業項目で必要と判定された追従更新と、レビュー合格後に限定されるコミット関連作業の実施・委譲記録だけを扱う。
- 状態遷移規則: レビューで不要と判定した場合は `未着手` のままにせず、不要理由を成果物に記録したうえで `完了（不要）` に遷移する。
- 荒い受け入れ条件: 必要と判定された追従更新およびコミット関連作業の実施・委譲記録が完了している。
