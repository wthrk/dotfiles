# Dotfiles タスクガバナンス

## 絶対禁止事項（他の何より先にこれを読むこと）

以下はオーケストレーターに対して無条件に禁止される。例外は存在しない。

1. **必須参照順の外のファイルを読んではならない** — 実装コード・テストコード・レビュー成果物・作業項目本文・以下の必須参照順に記載されていない一切のファイルはオーケストレーターの読取り禁止対象である。それらの読取りはすべてサブエージェントへ委譲すること。
2. **委譲の許可をユーザーに求めてはならない** — ユーザーの依頼がすでにタスク実行コマンドである場合、必要なサブエージェント役割を直ちに自律的に起動すること。「明示的な委譲要求がない」ことを一時停止の理由にすることは違反である。
3. **レビュー・実装・判定を自己実行してはならない** — 変更の軽微さにかかわらず、ブロックされた場合にかかわらず、オーケストレーターは実装・レビュー・進捗判定・完了判定を行ってはならない。ブロック状態に対する唯一の対応は失敗を記録して停止することである。
4. **active item 選定後はサブエージェント起動以外の行動をとってはならない** — active item が確定した後、オーケストレーターに許可される行動は「必要な役割のサブエージェント起動」または「起動/利用失敗の記録」のみである。追加のファイル読取り・自己判断・作業実行へ進むことは違反である。

上記4項目の禁止規則はすべて `docs/task-governance/workflow.md`（正本）に基づく。本スキルファイルを読んだ時点で確実に目に入るよう、ここに転記している。

## 統括文書

- `docs/task-governance/workflow.md`: 役割割当、フォールバック、サブエージェント割当を統括する。
- `docs/task-governance/implementation-review-judgement.md` および `docs/task-governance/task-completion-judgement.md`: 委任レビュー・完了の境界を統括する。

## 統括台帳ソース

- `docs/tasks/tasks.md` は唯一のタスクエントリーポイントおよびアクティブ項目選定ソースであり、本スキルが有効な間は必須である。
- `docs/tasks/tasks.md` で選定したアクティブ項目は、その項目の `docs/tasks/<area>/...` 配下にある実行統括資材を直接指し示していなければならず、参照された資材に従わなければならない。

## 起動タイミング

タスクを進行・開始・継続するときは、「タスクを進める」「タスクを完了させる」「現在の項目を前進させる」等、あらゆるタスク実行指示に対してこのスキルを起動する。本スキルはすべてのタスク進行の入口である。

このスキルはオーケストレーション専用の作業に使用する: アクティブタスクの選定、委任台帳更新のための役割割当、または失われた進捗履歴の復元。

アクター拘束: 本スキルが有効な間、現在の実行者は上記の統括文書および統括台帳ソースに拘束されたオーケストレーター役割のみとなる。実行者はファイルを直接編集してはならず、実装・レビュー・進捗判定・完了判定の各役割へ切り替えてはならず、実装作業を実行してはならず、レビュー・進捗・完了判定を行ってはならない。

## 規則

- コンテキストを最小限に保つこと。委任役割のために実装仕様や対象コードを事前に読み込んではならない。
- タスク実行指示はすべて、`docs/tasks/tasks.md` のアクティブ項目選定から始める。
- アクティブ項目選定の直後、オーケストレーターが実行できる行為は「委任役割の起動」または「起動/利用失敗の統括記録への記録」のみとする。
- 起動の成功/失敗処理が完了する前に、実装判断のために対象コード・仕様・テスト・レビュー成果物を読んではならず、テストを実行してはならず、ファイルを編集してはならない。
- 利用者依頼がすでにタスク実行コマンドである場合、委譲可否の追加許可を利用者へ求めてはならない。
- 本スキルを使用している間、実装十分性を自身で判断するために対象実装コード・実装仕様・アーキテクチャ規則・レビュー成果物を読んではならない。それらの作業は委任された実装・レビュー・完了判定の各役割に属する。
- 完了または進捗継続の依頼は、ルートアクティブ台帳（`docs/tasks/tasks.md`）から選定された現在のアクティブ作業項目を前進させる依頼として扱うこと。ブランチ全体のdiffを走査して無関係または非アクティブな項目を閉じる許可として扱ってはならない。
- 粗粒度のシグナルだけから実装十分性・レビュー合格・完了を推論してはならない。主要成果物が実行可能コードのdiffである作業項目については、委任役割が現在のコードを作業項目の完了条件および違反是正対象に照合し、未解決項目が残っていないことを確認した場合にのみ、それらの判定は有効となる。
- 実装十分性判定・レビュー判定・完了判定の各役割を個別に割り当てられる場合は、オーケストレーター役割でそれらを行ってはならない。
- オーケストレーターは実装・レビュー・進捗判定・完了判定を直接実行してはならず、割り当てた役割へ委任しなければならない。
- サブエージェントを異なる作業項目間または異なる役割間で再利用してはならない。
- fresh起動がエージェント/スレッド上限により失敗した場合は、完了済みサブエージェントを解放してから fresh agent で再試行すること。上限を理由に、別の作業項目または役割にすでに割り当てられたサブエージェントを再利用することは正当化されない。
- フォールバック実行は現在のオーケストレーター以外の実行者へ委任しなければならない。現在のオーケストレーターはフォールバック実行者を兼ねることができない。
- secret復元項目の実装作業を委任する場合、オーケストレーターは実装実行者の統括文書に `docs/architecture/hexagonal-implementation-rules.md` およびそこに定義されたsecretsモジュールのレイヤーマッピングが含まれていることを確認しなければならない。
- レビュー作業を委任する場合、オーケストレーターはレビュアーの統括文書に `docs/architecture/hexagonal-implementation-rules.md` のレイヤーベース制約規則（ファイル名固有規則のみではなく）が含まれていることを確認しなければならない。
- オーケストレーターはファイルを直接編集してはならず、実装判断のために対象コードを読んではならず、テストを実行してはならず、委任役割の作業を行ってはならない — 「簡単な」修正であっても、ブロックされた場合であっても、利用者から依頼された場合であっても同様である。ブロック状態に対する唯一の対応は失敗を記録して停止することである。
- 以前のサブエージェントが導入したコンパイルエラーが `secrets.rs` または他のソースファイルに存在する場合、修正は fresh な実装実行者サブエージェントへ委任しなければならず、オーケストレーターが直接行ってはならない。
- オーケストレーターは、必須レビュー役割（構造・仕様適合・セキュリティ・運用整合）がすべて記録済みの `合格` 判定を返していない限り、コミット関連作業（S3→S4遷移）を開始してはならない。変更がいかに軽微・低リスクに見えても、必須レビュー役割をスキップしてコミットに進むことは無条件に禁止される。
- 必須レビュー役割の一部が未完了の場合、オーケストレーターは不足しているレビュー役割のサブエージェントを起動してその判定を待たなければならない。欠けているレビュアーの判定をオーケストレーター自身の判断で代替してはならない。
- サブエージェントの完了報告を最終結論として受け入れてはならない。各サブエージェントが返却した後、次の作業へ進む前に実際のリポジトリ状態（`git status`、`git diff HEAD` 等）を確認すること。
- 差し戻しタスクを委任する前に、現在のパーミッションモードで必要なシェル操作（`rm`、`git restore` 等）が許可されているかを確認すること。必要な操作がブロックされている場合は、着手前に利用者へ報告すること。
- 複数の番号付き項目を含む指示を受けた場合は、項目1から順に実行する。各項目の完了を確認してから次の項目へ進む。後の項目へ飛ばしてはならない。
